dbt-hodor

Hold Old Data, Or Rebuild

Docs GitHub

Scheduled runs rebuild everything

A scheduled dbt run builds every model in scope, even when its code and its inputs are the same as yesterday. hodor checks each node first and reuses what did not change.

An example

The daily run of a large Databricks project (illustrative figures):

Every night the run builds all of it again. Most nodes read the same data as the day before.

What hodor changes

For each node hodor asks two questions: did the code change, and did new data arrive upstream? If both answers are no, the node keeps the table it already has.

Status: early development. The engine and the stores pass end-to-end tests on dbt-duckdb, and live tests on Databricks, Trino (Iceberg) and Snowflake. It has not run in a large production project yet. Start in shadow mode (tab 8) to see its decisions before it skips anything.

One job: hold the door

hodor holds the door in front of your warehouse, and that is the only decision it makes, once per node.

A node gets through to a rebuild only when its code changed or new data arrived upstream. Everything else keeps the data it already has.

How a run works

hodor runs inside the dbt process as a plugin. Step through one run, or press Play.

Play runs the remaining steps by itself; press Pause to stop. Step shows exactly one more step. Back goes one step back. Restart returns to step 1.

Fast path

When the compiled SQL text equals the text of the last build, hodor takes the stored analysis and skips sqlglot. Hashing a project of about 15,000 models then takes about 0.2 s instead of about 7 minutes (measured on a sample, single thread).

How the numbers are simulated

Queries: hodor reads the state once, runs one DESCRIBE HISTORY per upstream table (2 here), one refresh read per built table and one insert per 500 records. A built model counts 2 queries, a built test 1, a reused node 0. Wall clock: built nodes take fixed example times (views 1.2 s, tables 4.8 to 6.5 s, tests 2.4 s), a reused node 0.01 s, plus 1.1 s for hodor at the start and 0.4 s for the insert. Compute: 4 compute-seconds per second of a built node, 0.5 per hodor query. The comparison column is the same run with every node built and no hodor.

What dbt-hodor prints (simulated)

    Data versions

    hodor does not trust file timestamps. It asks each table for a data version, a token it compares for equality with the token recorded at the last build.

    Delta table history

    The token is the version and the commit time of the latest commit that changed data, so a recreated table whose versions restart still counts as changed. Maintenance commits never count. Other commits count, unless all their change metrics are 0.

      Maintenance operations that never count

      OPTIMIZE, VACUUM START, VACUUM END, ANALYZE, COMPUTE STATS, SET TBLPROPERTIES, UNSET TBLPROPERTIES, CHANGE COLUMN, ADD CONSTRAINT, DROP CONSTRAINT, UPGRADE PROTOCOL, SET TAGS, UNSET TAGS, CLUSTER BY, REORG, FSCK.

      Change metrics and the commit window

      Change metrics that decide the zero-row case: numOutputRows, numRemovedFiles, numTargetRowsInserted, numTargetRowsUpdated, numTargetRowsDeleted, numDeletedRows, numUpdatedRows, numCopiedRows. A commit with none of them counts as a change. A replace that writes 0 rows still removes the old files, so it counts: the table is now empty.

      Only the newest 20 commits are read (DESCRIBE HISTORY ... LIMIT 20). If none of them changed data, the version is unknown and dependents build. An unknown operation name counts as a change: that can cause an extra build, never a wrong reuse.

      DuckDB content fingerprint

      DuckDB has no table history. The token is the row count plus an order-independent sum of row hashes. Reordering rows keeps the token. Changing a value changes it. This suits local test data.

      Trino and Snowflake

      Trino: the Iceberg snapshot history and metadata log, or the Delta Lake commit history, read from the $history table. Other connectors have no history, so their tables are unknown and dependents build. Trino adapter.

      Snowflake: the SYSTEM$LAST_CHANGE_COMMIT_TIME token with the created and last_ddl times of the table. Snowflake adapter.

      What dbt-hodor prints (simulated)

      Lineage

      To know if upstream data changed, hodor needs the tables a node really reads. Sources and tables have their own version. Views and ephemerals have none, so hodor looks through them.

      looked throughits own version is usedunknown
      • A delta.`path` input has a version from its own Delta history.
      • read_files(...) and other table functions have no version. The node always builds.
      • One unknown input is enough to build the node (unknown_upstream).
      • A non-Delta source, such as a foreign table, is unknown too.

      Fail open

      Every error leads to a build, never to a reuse. hodor never fails a dbt run.

      FailureBehavior
      Exception while deciding a nodeWarning, normal build, reason hodor_error
      State store cannot be readWarning, the whole run builds
      State write failsWarning; those nodes build next run (no_history)
      Metadata query fails for a tableThat table is unknown; dependents build
      Invalid config valueWarning, default is used
      Ctrl+C or job cancelQueued records are flushed if possible

      Tests are replayed

      When nothing a test checks has changed, hodor returns the recorded result (pass, warn or fail) with the recorded failure count. The result line shows replayed. lag_tolerance is always 0 for tests.

      7 of 8 PASS not_null_fct_orders_id ......... [PASS (replayed) in 0.02s]

      The setup behind the scenarios

      The base target builds into analytics.sales; the CI target builds into analytics_ci.<ci_schema> through a generate_schema_name macro. The name of that schema can follow any scheme, for example pr_42_sales or mr_17_sales; hodor does not parse it. The PR edits fct_orders and adds rpt_orders. The CI job runs dbt build -s state:modified+ dim_parity --defer --state base-state; dim_parity is selected by name, though the PR does not change it. stg_orders is not selected, so dbt reads the base table through defer. See Slim CI in the docs.

      Docs

      Early development. The engine and stores pass end-to-end tests on dbt-duckdb and live tests on Databricks, Trino (Iceberg) and Snowflake. Not yet proven in a large production project.

      What it is

      A free, self-hosted alternative to dbt Labs' dbt State. It runs inside dbt as an auto-loaded plugin (module dbt_hodor). It needs no dbt platform account and sends nothing to external services. dbt-core 1.12.x; adapters dbt-databricks 1.12.7, dbt-trino 1.10.6 (Iceberg and Delta Lake connectors; Delta Lake connector: unit tests only), dbt-snowflake 1.12.4 (state in DuckDB or Postgres), and dbt-duckdb for local development and tests.

      Install

      Install dbt-hodor from PyPI in the environment where dbt runs. dbt loads any installed module named dbt_* that has a plugins list, so there is nothing to configure in dbt.

      pip install dbt-hodor
# local DuckDB state store:
pip install "dbt-hodor[duckdb]"

      Requires Python 3.10 or newer. If upstream dbt_state is also installed, hodor disables itself with a warning.

      CLI

      dbt-hodor explain shows why each node of the latest run was reused or built: the reason, the last build it was compared with, the code and config hashes then and now, and each upstream data version then and now. It only reads the state table. Options: -s (a unique_id, a relation or a name; repeat for more nodes), --invocation, --json, and dbt's --project-dir, --profiles-dir, --profile and -t. Try it in the Simulator tab.

      $ dbt-hodor explain -s fct_orders
dbt-hodor explain: hodor_e2e/local, invocation 7d1e4b90-... (2026-10-21 20:42 UTC), 1 node
model.hodor_e2e.fct_orders: build (new_upstream_data)
  last build   2026-10-20 20:41 UTC, invocation 1f0c2a7e-...
  code hash    same (qualify:6c1f02aa)
  config hash  same (e56f2a83)
  upstream     raw.orders: 14@1792465200000 -> 15@1792551600000

      dbt-hodor ddl prints the CREATE TABLE statement of the state table, for manual creation.

      dbt-hodor prune deletes the old records of this project and target. It is a dry run unless you pass --yes, and --keep-days N sets the window to keep (default hodor_lookback_days). Records of other projects and targets in the same table are never touched.

      $ dbt-hodor prune --keep-days 30
Would delete 1284 records: hodor_e2e/local, records older than 30 days.
Run again with --yes to delete them.

      Result lines carry the reason too:

      4 of 8 REUSED sql table model main.fct_orders ......... [REUSED (no_new_data) in 0.01s]
4 of 8 OK created sql table model main.fct_orders ......... [OK (new_upstream_data) in 0.07s]
4 of 8 OK created sql table model main.fct_orders ......... [OK (shadow, could reuse: no_new_data) in 0.06s]
7 of 8 PASS not_null_fct_orders_id ......... [PASS (replayed) in 0.02s]

      The last line of a run: dbt-hodor: N reused, M built, K fail-open errors. In shadow mode: dbt-hodor: N could be reused, M need a build (shadow: all built), K fail-open errors.

      Slim CI

      hodor works with -s state:modified+ --defer --state <prod manifest>, with or without --favor-state. Catalog and schema names of the project's own nodes are replaced by the node's id before hashing, so a CI catalog or a schema per pull request, under any naming scheme, is not a code change. Each push reuses what the last push built. A table made by dbt clone has no hodor record, so it builds once, then is reused. A deploy compares only with the target's own history. Try it in the Slim CI tab.

      Scope

      Commands: run, build, test, seed and snapshot.

      Supported: models materialized as table, incremental and view, plus seeds, snapshots and data tests. Incremental strategies: append, merge, delete+insert, insert_overwrite and replace_where; an unset strategy counts as merge.

      Built as plain dbt: Python models, microbatch, materialized views, streaming tables, metric views, custom materializations, custom incremental strategies and unit tests.

      A seed is reused when the CSV content (sha256 of the file, line endings normalized) and its config are unchanged and its table was not written outside dbt. A snapshot follows the table rules: code, config and upstream data unchanged, and its target not written outside dbt. lag_tolerance applies to snapshots too.

      Known limit

      A change to a materialization macro, for example a dbt-databricks upgrade, does not show in the compiled SQL. Run once with HODOR_MODE=off after such an upgrade.
